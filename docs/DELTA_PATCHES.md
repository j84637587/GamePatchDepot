# 差異補丁：只下載變更內容

更新：2026-10-04。

**發布端及 NovaLink 玩家端補丁流程已實作；真實大型客戶端與 R2 Test 端到端仍待實機驗收。**

## 現在怎麼用

原本流程不變：Prepare → Build → 本機驗證 → Upload → R2 深度驗證 → Test。

1. 第一版沒有舊內容，所以只建立完整分塊。
2. 第二版 Prepare 指定比較基準（UI 會選發布基準）。
3. Build 比較同一路徑的新舊內容，只為有變更的檔案產生額外補丁。
4. 產生後實際套用補丁，確認新檔大小與 SHA-256 都正確，才加入簽章清單。
5. Upload 同時上傳完整分塊與補丁，R2 深度驗證會核對兩者。

例如 `Map.nx` 在開頭插入資料，即使後面全部位移，也可比對舊內容產生二進位補丁，而不是只比較固定分塊位置。節省比例取決於真實內容，重新壓縮或大量重排仍可能產生很大的補丁。

新增檔案、未變更檔案、零位元組檔案不建立補丁。若補丁大小不小於新檔，則不保留補丁，仍保留完整下載方式。只產生本次比較基準到新版的單一步驟補丁，不產生歷史補丁鏈。

## 你需要保留什麼

- 本機必須有基準版本的 Manifest、簽章與完整 chunks。Build 會從它們重組出正確的舊檔，不相信任意來源資料夾內的舊檔。
- 缺少或損壞基準內容時，Build 會停止並說明原因，不會假裝補丁產生成功。
- 設定在 `config/product.json` 的 `enableDeltaPatches`，本專案已啟用。設為 `false` 可明確選擇只建立完整分塊的新版本。
- 工具安裝：`setup-patch-tools.ps1`，使用固定版本 HDiffPatch v5.1.3，核對套件及執行檔 SHA-256。
- Build 會顯示每個補丁大小；`reports/builds/<release>.json` 另外記錄 `patchCount`、`patchBytes`。
- 已簽章的版本不可事後追加補丁；新增功能適用於之後建立的新版本。

## 本機與 R2 存放位置

| 內容 | 位置 |
|---|---|
| 本機補丁快取 | `work/patches/<hash前兩碼>/<SHA-256>` |
| R2 補丁 | `objects/patches/sha256/<hash前兩碼>/<SHA-256>` |
| 原有完整分塊 | 仍使用 `objects/sha256/…` |
| 補丁適用條件 | 記錄於已簽章 Manifest 各檔案的 `patch` 欄位 |

GC 會保留保留版本引用的補丁；未被引用的補丁也遵守既有寬限規則。新增的 GC 範圍只包含 `objects/patches/sha256/`，不刪其他未知前綴。

## 玩家端接入規格

每個 Manifest 檔案仍有原本的 `path`、`size`、`sha256`、`chunks`，另外可能有：

```json
"patch": {
  "format": "hdiffpatch-sf20-zstd",
  "baseSha256": "舊檔的完整 SHA-256",
  "baseSize": 21474836480,
  "sha256": "補丁本身的 SHA-256",
  "size": 1048576,
  "key": "objects/patches/sha256/前兩碼/補丁SHA-256"
}
```

這是欄位示意，不是可直接使用的有效雜湊資料。新檔的大小與雜湊就是父層檔案的 `size`／`sha256`。`patch` 是可選欄位；沒有時使用完整分塊。

maplelink 應依下列順序處理：

1. 先驗證頻道與 Manifest 簽章、產品、版本、路徑及下載來源。不能依未驗章的清單執行更新。
2. 若檔案已符合目標 SHA-256，直接略過。
3. 若支援此補丁格式，且本機舊檔的大小、完整 SHA-256 符合 `baseSize`／`baseSha256`，才下載補丁。
4. 核對補丁大小與 SHA-256，再用固定、可信任的 hpatchz 套用到另外的 staging 檔案，不能直接覆寫玩家原檔。
5. 新檔大小及 SHA-256 符合目標後，才能進入原本的安全替換／交易流程。
6. 補丁不存在、格式不支援、基準不符、補丁下載或套用失敗時，由玩家端改用同一份已驗章 Manifest 的完整分塊重建；同樣驗證新檔後才替換。

**使用者取消不算補丁失敗，不可因此偷偷啟動完整下載。** 磁碟不足、遊戲占用或權限不足也應提示處理，盲目改下載完整檔案並不能解決。任何失敗都不得提交新版成功狀態。

NovaLink 的安裝與修復現共用補丁優先流程。僅在有有效安裝紀錄、本機基準大小與 SHA-256 符合、格式支援且沒有已驗證完整分塊可接續時嘗試補丁；其他情況沿用完整分塊。跳版基準不符時直接完整下載，不追補丁鏈。

固定版本 hpatchz 內嵌於啟動器，執行前驗證雜湊，不使用 PATH。補丁本身驗證大小／SHA-256，再核對 HDIFFSF20/zstd 標頭的基準與目標大小，套用到 `novapart` 的獨立暫存。成功重組並驗證完整 SHA-256 後，進入原有交易、備份與恢復流程。

補丁下載、格式、解碼或結果驗證失敗，只改完整下載該檔案。取消、工具遭修改、I/O、空間、權限與資源錯誤會停止，不自動完整下載。取消後完整且已驗證的補丁可重用；半個補丁下次重新下載，原本完整分塊接續不變。安裝完成清理已識別的補丁暫存，不清除未知檔案。

## 20 GB 檔案的重要限制

- 省的是玩家下載量，不代表不用讀寫完整新舊檔案。
- 發布端目前會逐檔重組一份舊檔，並產生一份套用驗證的新檔。20 GB 檔案可能需要約 40 GB 額外暫存，再加上補丁與既有 Candidate／chunks 空間；一次只處理一個檔案，正常完成或取消後清除本次暫存。
- 使用串流模式，不把 20 GB 新舊檔整份載入 RAM；比對仍需索引與壓縮記憶體，不宣稱固定記憶體上限。
- Build 若因磁碟不足或工具失敗停止，不會寫出可發布的補丁清單。
- R2 同時保存完整分塊與補丁，因此會增加儲存用量；這是換取更新流量減少與完整下載備援。

## 已驗證與待驗證

已驗證：檔案開頭插入資料、不同位置修改、真實 hdiffz／hpatchz 重組 SHA-256、一樣的 Build 重跑不改 Manifest、完整分塊保留、補丁太大時略過、基準損壞時拒絕、補丁上傳與深度雜湊驗證，以及 GC 引用保護。

測試範例：4,194,304 bytes 的隨機基準資料，開頭新增 45 bytes 並另修改一個位元組，目標 4,194,349 bytes，補丁 90 bytes。這是合成資料測試，不代表真實 NX 的補丁比例。

玩家端已加入真正補丁的自動化測試：成功時不下載完整分塊、補丁下載／格式／解碼／新檔驗證失敗時逐檔備援、基準缺少或不符時略過補丁、取消保留舊檔及版次、重新操作重用完整且已驗證的補丁、補丁工具被修改時拒絕執行。玩家端樣本為 746 bytes 舊檔、814 bytes 新檔、99 bytes 補丁，不代表大型遊戲的省流量比例。

待實機驗證：20 GB 真實 NX、低磁碟空間與長時間執行、玩家端跨版本取消／強制終止與回復，以及含補丁清單的完整 R2 Test 公開下載端到端流程。本次未上傳或發布實際版本。
